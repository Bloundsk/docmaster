Introduction

Le niveau débutant décrivait les briques : HTML, CSS, JavaScript, la différence entre ce qui tourne dans le navigateur et ce qui tourne sur un serveur, et l'adaptation aux écrans.

Ce niveau porte sur ce qui transforme une page en application : comment les morceaux se parlent, où les données vivent, comment tout cela arrive chez les visiteurs, et comment travailler à plusieurs sans se marcher dessus. Ce sont les quatre sujets sur lesquels un projet personnel devient un projet réel.

Avertissement

Ce guide est pédagogique et indépendant des technologies à la mode. Les principes exposés valent quel que soit le langage ou le cadriciel ; les outils changent, les mécanismes beaucoup moins.

Ce qui fait une application

🔌 Les API et le JSON

Une API est le point de contact entre deux programmes. Sur le web, elle prend presque toujours la même forme : le navigateur envoie une requête à une adresse, le serveur renvoie des données structurées — le plus souvent au format JSON.

Un contrat, pas seulement une adresse

Une API bien conçue définit quatre choses : l'adresse et la méthode, ce qu'on envoie, ce qu'on reçoit, et ce qui se passe quand ça échoue. Le dernier point est celui qu'on oublie, et c'est celui qui fait tomber les applications en production.

Les codes de retour ont un sens précis : 200 tout va bien, 400 la demande est mal formée, 401 il faut s'identifier, 404 la ressource n'existe pas, 500 le serveur a échoué. Renvoyer 200 avec un message d'erreur dans le corps oblige chaque client à deviner.

Exemple chiffré — le coût des allers-retours

Une page qui enchaîne 8 appels d'API, chacun avec 120 ms de latence réseau et 30 ms de traitement serveur.

En séquence : 1 200 ms. En parallèle, quand les appels ne dépendent pas les uns des autres : environ 150 ms.

Le serveur n'est pas plus rapide dans le second cas. C'est l'organisation des appels qui change tout.

Erreur fréquente — la clé d'API dans le code du navigateur

Tout ce que le navigateur reçoit est lisible : le code JavaScript, les variables, les en-têtes. Une clé secrète placée là est publique, même « minifiée ».

Les appels qui nécessitent un secret doivent passer par votre propre serveur, qui détient la clé et relaie la demande.

💡 Le temps d'une page dépend surtout du nombre d'allers-retours, rarement de la vitesse du serveur.

🗄️ Les bases de données

Dès qu'une application conserve quelque chose entre deux visites, elle a besoin d'une base de données. Le choix du type compte moins qu'on ne le dit ; la façon de l'interroger compte énormément.

Relationnel ou documents

Une base relationnelle range les données en tables liées entre elles, avec un schéma défini à l'avance. Elle garantit la cohérence : impossible d'enregistrer une commande sans client existant.

Une base documentaire stocke des objets complets, sans schéma imposé. Elle est plus souple au démarrage, et déplace la responsabilité de la cohérence dans le code.

Pour la grande majorité des projets, le relationnel reste le choix par défaut raisonnable : les données finissent presque toujours par avoir des relations, et il vaut mieux que la base les fasse respecter.

Exemple chiffré — le problème des requêtes en boucle

Afficher 50 articles avec le nom de leur auteur.

Une requête par auteur : 1 requête pour les articles, puis 50 requêtes. À 4 ms chacune, cela fait 204 ms.

Une seule requête avec jointure : environ 6 ms.

Le rapport est de 34 pour 1. Sur 500 articles, il devient catastrophique — alors que le code paraît identique.

Les index, et leur prix

Un index accélère la recherche sur une colonne, comme l'index d'un livre. Sans lui, la base parcourt toutes les lignes. Avec, elle va directement au bon endroit.

Le prix : chaque index ralentit un peu les écritures et occupe de l'espace. Indexer les colonnes utilisées dans les filtres et les jointures, pas toutes.

Erreur fréquente — construire une requête en collant du texte

Assembler une requête en concaténant ce que l'utilisateur a saisi ouvre la porte à l'injection SQL — l'une des vulnérabilités les plus anciennes et les plus exploitées.

La parade est simple et systématique : les requêtes préparées, où les valeurs sont transmises séparément du texte de la requête. Aucune raison de faire autrement, jamais.

💡 Une requête dans une boucle est le défaut de performance le plus courant, et le plus invisible à la lecture.

🚀 Mettre en ligne

Un site qui fonctionne sur votre machine ne fonctionne pas encore. La mise en ligne ajoute des contraintes que le développement local masque entièrement.

Les quatre éléments

Un nom de domaine, loué à l'année. Un hébergement, qui exécute votre code et sert vos fichiers. Un certificat, qui active le HTTPS — aujourd'hui gratuit et automatique chez la plupart des hébergeurs. Un moyen de déployer, c'est-à-dire d'envoyer une nouvelle version sans casser la précédente.

Pour un site sans code serveur, l'hébergement statique suffit : il est souvent gratuit, très rapide, et n'a presque rien à maintenir.

Ce qui change entre local et production

Les chemins ne sont pas les mêmes. Un lien qui fonctionne en local peut pointer nulle part une fois en ligne.

La casse compte. Windows ne distingue pas Image.png de image.png ; le serveur, si. C'est la panne la plus fréquente d'une première mise en ligne.

Les secrets ne peuvent plus être dans le code : ils passent par des variables d'environnement.

Le cache apparaît. Une modification peut sembler absente alors qu'elle est déployée.

Erreur fréquente — déployer en copiant quelques fichiers

Envoyer manuellement « les fichiers modifiés » conduit tôt ou tard à en oublier un. Le site référence alors un script absent, et casse pour tout le monde.

Déployez toujours l'ensemble, depuis une source unique — idéalement automatiquement, à partir du dépôt de code.

💡 La différence entre « ça marche chez moi » et « c'est en ligne » tient dans quatre points, tous vérifiables en une fois.

🧰 Travailler à plusieurs

Git est présenté comme un outil de sauvegarde. C'est inexact et cela conduit à mal s'en servir. Git sert à revenir en arrière et à travailler à plusieurs sur le même code sans se marcher dessus.

Ce qu'un bon historique permet

Un historique lisible répond à des questions concrètes : quand cette ligne a-t-elle changé, pourquoi, et quoi d'autre a bougé en même temps. Cela suppose des commits petits, cohérents, et accompagnés d'un message qui explique le pourquoi plutôt que le quoi.

« Correction du calcul de TVA sur les remboursements partiels » vaut infiniment mieux que « fix ». Le second oblige à lire le code pour comprendre.

Les branches

Une branche isole un travail en cours. Le principe : la branche principale reste toujours fonctionnelle, et chaque chantier vit à côté jusqu'à être prêt.

Une branche qui vit trois semaines devient très difficile à réintégrer : le reste a bougé pendant ce temps. Des branches courtes, fusionnées souvent, évitent l'essentiel des conflits.

Ce qui protège vraiment

Ne jamais commiter de secrets. Un mot de passe poussé une fois reste dans l'historique, même supprimé ensuite. Il faut le considérer comme compromis et le changer.

Un fichier d'exclusion dès le premier jour : dépendances, fichiers de configuration locale, journaux.

Relire avant de fusionner. Même seul : relire son propre changement une heure après l'avoir écrit fait apparaître ce qu'on ne voyait plus.

Erreur fréquente — le commit fourre-tout

Un commit qui mélange une correction, une nouvelle fonctionnalité et une remise en forme du code est impossible à annuler proprement : on ne peut pas retirer l'un sans les autres.

Un commit, une intention. C'est ce qui rend l'historique utilisable le jour où il faut défaire quelque chose.

💡 Git ne vous protège pas de la perte de fichiers. Il vous protège de l'impossibilité de revenir en arrière.

📚 Pour aller plus loin

  • MDN Web Docs : la référence sur HTTP, les codes de retour et les API du navigateur. Gratuite, sans publicité, et maintenue par la communauté.
  • Documentation officielle de Git : le chapitre sur les branches et la fusion, plus clair que la plupart des tutoriels.
  • OWASP : la liste des vulnérabilités les plus répandues, dont l'injection SQL. À lire avant d'écrire une requête, pas après.

Un réflexe utile : dès qu'une page semble lente, comptez le nombre de requêtes qu'elle déclenche avant d'optimiser quoi que ce soit d'autre.
