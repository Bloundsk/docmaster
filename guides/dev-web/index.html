💻 Développement Web

Apprendre à créer des sites et applications web modernes.

⚡ Points clés à retenir

  • HTML structure le contenu, CSS définit son apparence visuelle.
  • JavaScript rend une page interactive en réagissant aux actions de l'utilisateur.
  • Le frontend est ce que l'utilisateur voit, le backend gère la logique invisible côté serveur.
  • Le responsive design garantit un bon affichage sur tous les écrans.
  • L'approche mobile-first est de plus en plus recommandée.

Introduction

Le développement web a une particularité rare : on peut afficher un résultat visible en dix minutes, sans rien installer, avec un simple éditeur de texte et un navigateur. Cette barrière d'entrée très basse explique qu'on puisse y progresser en autodidacte.

Elle explique aussi la principale difficulté : l'écosystème est immense et bruyant. On y croise en permanence des outils présentés comme indispensables et qui ne le sont pas. Or les fondations, elles, n'ont pas bougé depuis vingt ans — HTML, CSS, JavaScript. Tous les frameworks du monde finissent par produire ces trois choses-là.

Ce guide s'en tient à ce qui reste vrai dans dix ans : la structure d'une page, sa mise en forme, son interactivité, la séparation entre ce qui tourne chez le visiteur et ce qui tourne sur un serveur, et l'adaptation aux écrans.

Les bases à connaître

🏗️ HTML & CSS

HTML décrit ce qu'est un contenu. CSS décrit à quoi il ressemble. Cette séparation est le premier principe du métier, et le premier qu'on enfreint quand on débute.

HTML : le sens avant l'apparence

Une balise porte une signification, pas un style. <h1> ne veut pas dire « gros texte » mais « titre principal de cette page ». La distinction n'est pas théorique : elle détermine ce que comprennent Google et les lecteurs d'écran.

Deux écritures, un même rendu visuel

<div class="titre-gros">Nos tarifs</div>
Pour un logiciel : un bloc quelconque contenant du texte.

<h2>Nos tarifs</h2>
Pour un logiciel : un titre de section. Un utilisateur aveugle peut y naviguer directement, un moteur de recherche sait de quoi parle la page.

Visuellement identiques après quelques lignes de CSS. Fonctionnellement, sans commune mesure.

Les balises structurantes à connaître : header, nav, main, section, article, aside, footer. Une page qui les utilise correctement est accessible presque sans effort supplémentaire.

CSS : la cascade et les sélecteurs

Quand deux règles s'appliquent au même élément, celle dont le sélecteur est le plus spécifique l'emporte — pas celle écrite en dernier. Un identifiant bat une classe, qui bat une balise. La plupart des « ce CSS ne marche pas » viennent de là.

Pour la mise en page, deux outils suffisent aujourd'hui : Flexbox pour aligner sur une ligne ou une colonne, Grid pour une grille à deux dimensions.

Enfin, les variables CSS centralisent les valeurs répétées :

Variables CSS

:root { --primary: #2563eb; }
puis color: var(--primary); partout où la couleur sert.

Changer la charte du site revient alors à modifier une seule ligne, au lieu de chercher un code hexadécimal dans quarante fichiers.

Erreur fréquente — écrire le style dans le HTML

<p style="color:red"> fonctionne, et devient ingérable dès la dixième page : chaque modification impose de rouvrir tous les fichiers.

Le style va dans un fichier .css séparé. Cette discipline coûte cinq minutes au début et fait gagner des journées ensuite.

💡 HTML répond à « qu'est-ce que c'est ? », CSS à « à quoi ça ressemble ? ». Tant que la réponse est claire, le code reste maintenable.

⚡ JavaScript

HTML et CSS produisent une page figée. JavaScript la rend vivante : il réagit aux actions, modifie le contenu et communique avec des serveurs, sans recharger la page.

Le DOM

Quand le navigateur lit le HTML, il en construit une représentation en mémoire : le DOM (Document Object Model). C'est cette structure que JavaScript manipule — jamais le fichier d'origine.

Conséquence pratique : le fichier HTML sur le disque ne change pas. Actualiser la page annule tout. C'est pourquoi une information à conserver doit être enregistrée quelque part — localStorage dans le navigateur, ou un serveur.

Le schéma de base : sélectionner, écouter, agir

const bouton = document.getElementById('menu');
bouton.addEventListener('click', () => {
  menu.classList.toggle('ouvert');
});

Trois lignes qui résument 80 % du JavaScript d'un site : on récupère un élément, on écoute un événement, on modifie une classe. Le style reste dans le CSS — JavaScript se contente d'ajouter ou retirer la classe.

Synchrone et asynchrone

Certaines opérations prennent du temps : interroger un serveur, lire un fichier. JavaScript ne s'arrête pas à les attendre — il continue et traite la réponse à son arrivée. C'est ce qu'on appelle l'asynchrone.

D'où le mot-clé await, qui signifie « attends le résultat avant de poursuivre cette fonction ». Sans lui, on manipule une réponse qui n'est pas encore arrivée — une des causes les plus fréquentes de bugs incompréhensibles chez les débutants.

Les outils du navigateur

La touche F12 ouvre les outils de développement. Trois onglets valent tous les tutoriels :

  • Console : les erreurs JavaScript s'y affichent, avec le numéro de ligne.
  • Réseau : chaque fichier chargé, avec son code de retour. Un 404 en rouge s'y repère immédiatement.
  • Éléments : le DOM réel, et le CSS effectivement appliqué à chaque élément.
Erreur fréquente — le script exécuté trop tôt

Un script placé dans le <head> s'exécute avant que le HTML n'existe. getElementById renvoie alors null, et tout s'arrête.

Deux solutions : placer le script juste avant </body>, ou ajouter l'attribut defer. C'est l'erreur numéro un des premiers projets.

💡 Avant de chercher pourquoi « ça ne marche pas », ouvrez la console. L'erreur y est presque toujours écrite, avec sa ligne exacte.

🔗 Frontend et Backend

La question qui départage les deux : ce code s'exécute-t-il sur la machine du visiteur, ou sur un serveur que vous contrôlez ?

FrontendBackend
S'exécuteDans le navigateur du visiteurSur un serveur
LangagesHTML, CSS, JavaScriptNode.js, Python, PHP, Java…
RôleAffichage, interactionsDonnées, comptes, paiements
Visible par le visiteurEntièrementJamais

La conséquence la plus importante

Tout ce qui part vers le navigateur est lisible : code, commentaires, clés d'accès. Un simple clic droit suffit.

Erreur fréquente — et coûteuse

Placer une clé d'API, un mot de passe de base de données ou une vérification d'accès dans le JavaScript revient à les publier. Des robots parcourent en permanence les sites et les dépôts publics à la recherche de ces clés ; le délai entre publication et exploitation se compte souvent en minutes.

Toute vérification qui compte — droits, paiement, quota — se fait côté serveur. Le contrôle côté navigateur n'est là que pour le confort d'usage : il se contourne en quelques secondes.

Les sites statiques

Tous les projets n'ont pas besoin d'un serveur. Un site de contenu — documentation, portfolio, blog — peut être constitué de fichiers HTML servis tels quels. C'est plus rapide, gratuit à héberger, et pratiquement inattaquable : il n'y a pas de base de données à pirater.

Le backend devient nécessaire dès qu'il faut des comptes utilisateurs, des données modifiables, des paiements ou des envois de courriels.

Les frameworks

React, Vue, Angular résolvent un problème précis : synchroniser une interface complexe avec des données qui changent sans arrêt. Sur une application de gestion, ils font gagner beaucoup. Sur un site de dix pages, ils ajoutent surtout de la complexité et du poids.

Le bon ordre d'apprentissage est celui du besoin : maîtriser JavaScript, rencontrer la limite, puis choisir l'outil qui la résout.

💡 Tout ce qui arrive dans le navigateur est public. La sécurité ne s'écrit jamais côté frontend.

📱 Responsive Design

La majorité du trafic web se fait aujourd'hui sur mobile. Un site qui n'est pas utilisable sur un écran de 6 pouces est un site qui ne fonctionne pas — quelle que soit son allure sur l'écran du développeur.

Les trois ingrédients

  1. La balise viewport dans le <head> :
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    Sans elle, le mobile affiche une version miniature du site en 980 px. C'est la première chose à vérifier.
  2. Des unités souples : %, rem, fr, max-width. Une largeur fixe en pixels déborde forcément sur un écran plus étroit.
  3. Les media queries : des règles CSS conditionnées à la taille de l'écran.
L'approche mobile-first

On écrit d'abord le style pour petit écran, puis on ajoute pour les grands :

.grille { display: block; }
@media (min-width: 768px) {
  .grille { display: grid; grid-template-columns: 1fr 1fr; }
}

Pourquoi commencer par le mobile ? Parce qu'un écran étroit oblige à hiérarchiser : il n'y a de place que pour l'essentiel. Faire l'inverse conduit à entasser puis à masquer — et à charger des éléments invisibles.

Ce qu'on oublie souvent

  • Les zones tactiles. Un doigt n'est pas un curseur : comptez au moins 44 pixels de côté pour tout élément cliquable.
  • Le survol n'existe pas. Un menu qui s'ouvre au passage de la souris est inaccessible au tactile.
  • Les images. Une photo de 4 000 px envoyée sur mobile consomme des données et ralentit tout. max-width: 100% évite au moins le débordement.
  • Les tableaux. Ils débordent presque toujours : placez-les dans un conteneur en overflow-x: auto.
Erreur fréquente — tester en réduisant la fenêtre

Rétrécir son navigateur donne une idée de la mise en page, mais ne reproduit ni le tactile, ni la densité de pixels, ni la lenteur du réseau mobile.

Le mode appareil mobile des outils de développement (F12) est plus fidèle. Et un test sur un vrai téléphone, au moins une fois avant publication, révèle presque toujours quelque chose.

💡 Concevez d'abord pour l'écran le plus contraint. Ce qui survit à cette contrainte est l'essentiel ; le reste était probablement superflu.

📚 Pour aller plus loin

  • MDN Web Docs — la documentation de référence, en français, maintenue par Mozilla. En cas de doute sur une balise ou une propriété, c'est ici et nulle part ailleurs.
  • web.dev (Google) — bonnes pratiques de performance et d'accessibilité, avec des cas mesurés plutôt que des opinions.
  • Can I Use — quelle fonctionnalité marche dans quel navigateur, et depuis quelle version.
  • Flexbox Froggy et Grid Garden — deux jeux gratuits qui font assimiler Flexbox et Grid en une heure chacun. Le meilleur rapport temps/résultat du domaine.
  • Lighthouse — intégré aux outils de développement (F12, onglet Lighthouse). Il note votre page sur la performance, l'accessibilité et le référencement, et liste ce qu'il faut corriger.

Conseil de méthode : la meilleure progression vient d'un projet qui vous tient à cœur, pas d'un tutoriel supplémentaire. Un site réel confronte à des problèmes réels — et c'est en cherchant à les résoudre qu'on retient.
