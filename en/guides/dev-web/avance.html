💻 Web Development — Advanced

What separates a site that works from a site that lasts.

🕒 Last updated: 5 September 2026

⚡ Key points

  • Caching is the only lever that improves performance without slimming anything down.
  • Any data coming from outside is hostile until proven otherwise.
  • A test that fails at random is worse than no test: it teaches people to ignore alerts.
  • Technical debt is not a moral failing, it is a loan — the problem is the interest.
  • A complete rewrite fails more often than it succeeds.

Introduction

The intermediate level was about building: making the pieces talk, storing data, going live, working with others. Enough to ship an application that works.

This level is about what decides its lifespan: holding up under load, resisting attacks, being changeable without fear, and ageing without becoming unreadable. Four subjects that are invisible on launch day, and that decide everything afterwards.

Warning

This guide is educational. The vulnerabilities described are there to be understood and avoided at the design stage. Performance orders of magnitude depend heavily on context: measure on your own system rather than trusting a figure read somewhere.

What decides the lifespan

⚡ Performance and caching

2 min Optimising without measuring is guessing.

Optimising without measuring is guessing. The first step is always the same: open the browser tools, look at what takes time, and attack the biggest bar — not the most interesting one.

Caching, the only free lever

Slimming a file down takes work. Caching it takes one line of configuration, and removes its download entirely for returning visitors.

The mechanism: the server states how long a file stays valid. While that period runs, the browser asks for nothing — not even to check.

Hence a constraint: a heavily cached file can no longer be changed in place. The universal solution is the versioned name: style.a3f9.css. A change alters the name, therefore the address, so the cache is bypassed naturally.

Worked example — the effect of caching

A page of 1,800 kB, of which 1,500 kB are static files — scripts, styles, fonts, images.

If 60% of visits are returns, those visitors download only 300 kB.

Average volume per visit: 900 kB instead of 1,800. Half as much, without having slimmed anything down.

What weighs, in order

In the vast majority of cases: images first — badly sized, in an old format —, then third-party scripts — analytics, widgets, banners —, then the application's own code.

Starting by optimising your own code while a 4 MB image sits at the top of the page is a frequent error of priority.

Common mistake — the page that shifts while loading

An image with no declared dimensions, a font replacing another, a banner slotting in: content moves under your fingers, and the user clicks the wrong thing.

Declaring image dimensions and reserving space for deferred elements removes this fault, without speeding anything up.

💡 Measure first. The cause of slowness is almost never the one you imagine.

🔐 Application security

1 min A single principle settles most of it: any data coming from outside is hostile until proven otherwise .

A single principle settles most of it: any data coming from outside is hostile until proven otherwise. Forms, addresses, headers, uploaded files, responses from a third-party API.

The three attacks to know

SQL injection: a query built by concatenation lets the user write part of the query. Defence: prepared statements, systematically.

Injected script — often called XSS: user content displayed as it stands can contain code, which will run for other visitors. Defence: escape on output, and set a content security policy.

Forged request — CSRF: a third-party site triggers an action on yours by taking advantage of the visitor's open session. Defence: a unique token per form, and cookies configured not to travel to other sites.

The defences that cost least

Validate on input, escape on output. Two distinct acts: the first refuses what does not have the expected shape, the second neutralises what is displayed.

Never trust the browser. A client-side check improves comfort; it can be bypassed in three seconds. The check that counts is the server's.

Update your dependencies. Most breaches come through a known, un-updated library, not through a novel flaw.

Common mistake — error messages that say too much

An error page showing the SQL query, the file paths or the server version hands an attacker a free map.

In production: a generic message for the visitor, the full detail in the logs. Both, never the reverse.

💡 Security is not added at the end. It consists of never trusting, from the first line.

🧪 Automated testing

2 min Tests do not exist to prove the code is correct: they exist so that it can be changed without fear .

Tests do not exist to prove the code is correct: they exist so that it can be changed without fear. A project with no tests becomes a project nobody dares touch, and that is how it dies.

Three levels, three uses

Unit tests check one isolated function. Fast — a few milliseconds — they say precisely what breaks.

Integration tests check that several pieces work together, database included. Slower, closer to reality.

End-to-end tests drive a real browser through a complete journey. The slowest and the most fragile, but the only ones that check what the user experiences.

The classic proportion: many unit tests, a few integration ones, very few end-to-end. The reverse produces a slow suite nobody waits for any more.

Worked example — the duration of a suite

400 unit tests at 5 ms: 2 seconds.

60 integration tests at 200 ms: 12 seconds.

12 end-to-end tests at 8 s: 96 seconds.

Total: 110 seconds, of which 87% for 2.5% of the tests. It is this handful of slow tests that decides whether the suite runs on every change, or once a week.

What to test first

Business logic — calculations, rules, edge cases — and critical journeys: sign-up, payment, sending. The rest can wait.

What does not deserve a test: trivial getters, library code, and the exact appearance of a screen, which will change anyway.

Common mistake — the flaky test

A test that fails one time in ten for no reason teaches the team to rerun without looking. The day it detects a real problem, nobody believes it.

A flaky test must be fixed or deleted — never tolerated.

💡 Tests do not exist to catch bugs: they exist to make change possible.

🏗️ Technical debt

2 min The metaphor is accurate: you borrow time today — by simplifying, by working around — and you repay it later, with interest.

The metaphor is accurate: you borrow time today — by simplifying, by working around — and you repay it later, with interest. The problem is not borrowing, it is never repaying.

Chosen debt and inherited debt

Chosen debt is owned: "we ship fast to validate the idea, we will come back to this module". It is documented and dated.

Inherited debt comes from ignorance or haste. Nobody knows it exists until they trip over it.

The first can be managed. The second builds up silently, until the slightest change becomes long and risky.

Worked example — the interest

A shaky architecture costs 3 hours a week in workarounds and fixes.

Over a year: 144 hours, that is nearly four weeks of work.

If fixing it takes 40 hours, the operation pays for itself in under four months. Put that way, the trade-off is no longer a matter of taste.

Rewriting, rarely

The temptation to start again is strong in front of old code. It usually fails, for one precise reason: the existing code contains years of fixes for special cases that nobody remembers, and that the rewrite will lose.

Gradual refactoring — replacing one piece at a time, keeping the rest working — is less gratifying and far safer.

Common mistake — the invisible debt in dependencies

A library not updated for two years becomes very hard to move forward: the intermediate versions introduced breaking changes that now all have to be crossed at once.

Updating regularly, in small steps, costs far less than one big jump every three years — and closes known vulnerabilities along the way.

💡 Put the debt in hours lost per week. It is the only language that gets you time to fix it.

📚 Going further

  • OWASP Top 10: the ten most widespread vulnerabilities, with vulnerable and fixed code examples. The reference in the field.
  • MDN — HTTP caching headers: the documentation that actually explains the difference between the directives, which are often misunderstood.
  • Browser audit tools: they give performance metrics and a list of recommendations ranked by gain.
  • “Working Effectively with Legacy Code”, Michael Feathers: how to add tests to code that has none, without breaking everything.
  • Vulnerability databases: they let you check whether a dependency you use is affected by a known flaw.

A useful habit: before proposing a rewrite, measure the time lost each week because of the current code. The figure changes the conversation.
