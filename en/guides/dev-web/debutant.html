💻 Web Development — Beginner

Understanding what a web page is made of. No programming background needed.

🕒 Last updated: 17 August 2026

📑 Contents

  • Introduction
  • 🏗️ HTML & CSS
  • ⚡ JavaScript
  • 🔗 Frontend and backend
  • 📱 Responsive design

⚡ Key points

  • HTML structures the content, CSS defines how it looks.
  • JavaScript makes a page interactive by reacting to what the user does.
  • The frontend is what the user sees, the backend handles the invisible logic on the server.
  • Responsive design ensures a page displays properly on every screen.
  • The mobile-first approach is increasingly recommended.

Introduction

Web development has a rare quality: you can display a visible result in ten minutes, with nothing installed, using a plain text editor and a browser. That very low barrier to entry explains why people can make progress on their own.

It also explains the main difficulty: the ecosystem is vast and noisy. You constantly meet tools presented as indispensable that are not. The foundations, meanwhile, have not moved in twenty years — HTML, CSS, JavaScript. Every framework in the world ends up producing those three things.

This guide sticks to what will still be true in ten years: the structure of a page, its styling, its interactivity, the split between what runs on the visitor's machine and what runs on a server, and adapting to screens.

The basics

🏗️ HTML & CSS

HTML describes what a piece of content is. CSS describes what it looks like. That separation is the first principle of the trade, and the first one broken by beginners.

HTML: meaning before appearance

A tag carries a meaning, not a style. <h1> does not mean "big text" but "main heading of this page". The distinction is not theoretical: it determines what Google and screen readers understand.

Two ways of writing, one visual result

<div class="big-title">Our pricing</div>
To software: a generic block containing text.

<h2>Our pricing</h2>
To software: a section heading. A blind user can navigate straight to it, a search engine knows what the page is about.

Visually identical after a few lines of CSS. Functionally, worlds apart.

The structural tags worth knowing: header, nav, main, section, article, aside, footer. A page that uses them correctly is accessible with almost no extra effort.

CSS: the cascade and selectors

When two rules apply to the same element, the one whose selector is more specific wins — not the one written last. An id beats a class, which beats a tag. Most "this CSS doesn't work" comes from there.

For layout, two tools are enough today: Flexbox to align along a row or a column, Grid for a two-dimensional grid.

Finally, CSS variables centralise repeated values:

CSS variables

:root { --primary: #2563eb; }
then color: var(--primary); everywhere the colour is used.

Changing the site's palette then means editing a single line, instead of hunting a hex code through forty files.

Common mistake — writing style inside the HTML

<p style="color:red"> works, and becomes unmanageable by the tenth page: every change means reopening every file.

Style belongs in a separate .css file. That discipline costs five minutes at the start and saves days afterwards.

💡 HTML answers "what is this?", CSS answers "what does it look like?". As long as the answer is clear, the code stays maintainable.

⚡ JavaScript

HTML and CSS produce a fixed page. JavaScript brings it to life: it reacts to actions, changes the content and talks to servers, without reloading the page.

The DOM

When the browser reads the HTML, it builds a representation of it in memory: the DOM (Document Object Model). That structure is what JavaScript manipulates — never the original file.

Practical consequence: the HTML file on disk does not change. Refreshing the page undoes everything. This is why information that must be kept has to be saved somewhere — localStorage in the browser, or a server.

The basic pattern: select, listen, act

const button = document.getElementById('menu');
button.addEventListener('click', () => {
  menu.classList.toggle('open');
});

Three lines that sum up 80% of a site's JavaScript: get an element, listen for an event, change a class. The styling stays in the CSS — JavaScript merely adds or removes the class.

Synchronous and asynchronous

Some operations take time: querying a server, reading a file. JavaScript does not stop to wait for them — it carries on and handles the answer when it arrives. That is what is called asynchronous.

Hence the keyword await, which means "wait for the result before continuing this function". Without it, you manipulate an answer that has not arrived yet — one of the most frequent causes of baffling bugs for beginners.

The browser's tools

The F12 key opens the developer tools. Three tabs are worth every tutorial:

  • Console: JavaScript errors appear there, with the line number.
  • Network: every file loaded, with its status code. A 404 in red is spotted immediately.
  • Elements: the real DOM, and the CSS actually applied to each element.
Common mistake — the script that runs too early

A script placed in the <head> runs before the HTML exists. getElementById then returns null, and everything stops.

Two solutions: put the script just before </body>, or add the defer attribute. It is the number one error of first projects.

💡 Before hunting for why "it doesn't work", open the console. The error is almost always written there, with its exact line.

🔗 Frontend and backend

The question that separates the two: does this code run on the visitor's machine, or on a server you control?

FrontendBackend
RunsIn the visitor's browserOn a server
LanguagesHTML, CSS, JavaScriptNode.js, Python, PHP, Java…
RoleDisplay, interactionsData, accounts, payments
Visible to the visitorEntirelyNever

The most important consequence

Everything sent to the browser can be read: code, comments, access keys. A right-click is enough.

Common mistake — and an expensive one

Putting an API key, a database password or an access check in the JavaScript amounts to publishing them. Robots constantly scan sites and public repositories looking for those keys; the delay between publication and exploitation is often measured in minutes.

Every check that matters — permissions, payment, quota — happens on the server. The browser-side check is only there for convenience: it can be bypassed in seconds.

Static sites

Not every project needs a server. A content site — documentation, portfolio, blog — can be made of HTML files served as they are. It is faster, free to host, and practically unattackable: there is no database to breach.

A backend becomes necessary as soon as you need user accounts, editable data, payments or emails.

Frameworks

React, Vue and Angular solve one precise problem: keeping a complex interface in step with data that changes constantly. On a business application they save a great deal. On a ten-page site they mostly add complexity and weight.

The right order of learning is the order of need: master JavaScript, meet the limit, then choose the tool that solves it.

💡 Everything that reaches the browser is public. Security is never written on the frontend.

📱 Responsive design

Most web traffic today happens on mobile. A site that is not usable on a 6-inch screen is a site that does not work — whatever it looks like on the developer's monitor.

The three ingredients

  1. The viewport tag in the <head>:
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    Without it, a phone shows a miniature version of the site at 980 px. It is the first thing to check.
  2. Flexible units: %, rem, fr, max-width. A fixed width in pixels necessarily overflows on a narrower screen.
  3. Media queries: CSS rules conditioned on the screen size.
The mobile-first approach

You write the style for the small screen first, then add for the large ones:

.grid { display: block; }
@media (min-width: 768px) {
  .grid { display: grid; grid-template-columns: 1fr 1fr; }
}

Why start with mobile? Because a narrow screen forces prioritising: there is room only for the essentials. Doing the reverse leads to piling things up then hiding them — and to loading elements nobody sees.

What is often forgotten

  • Touch areas. A finger is not a cursor: allow at least 44 pixels on a side for anything clickable.
  • Hover does not exist. A menu that opens when the mouse passes over it is unreachable on touch.
  • Images. A 4,000 px photo sent to a phone consumes data and slows everything down. max-width: 100% at least prevents overflow.
  • Tables. They almost always overflow: put them in a container with overflow-x: auto.
Common mistake — testing by shrinking the window

Narrowing your browser gives an idea of the layout, but reproduces neither touch, nor pixel density, nor the slowness of a mobile network.

The device mode in the developer tools (F12) is more faithful. And a test on a real phone, at least once before publishing, almost always reveals something.

💡 Design for the most constrained screen first. What survives that constraint is the essential; the rest was probably surplus.

📚 Going further

  • MDN Web Docs — the reference documentation, maintained by Mozilla. When in doubt about a tag or a property, look here and nowhere else.
  • web.dev (Google) — performance and accessibility good practice, with measured cases rather than opinions.
  • Can I Use — which feature works in which browser, and from which version.
  • Flexbox Froggy and Grid Garden — two free games that make Flexbox and Grid stick in an hour each. The best time-to-result ratio in the field.
  • Lighthouse — built into the developer tools (F12, Lighthouse tab). It scores your page on performance, accessibility and search visibility, and lists what to fix.

A method tip: the best progress comes from a project you care about, not from one more tutorial. A real site confronts you with real problems — and it is in trying to solve them that things stick.
