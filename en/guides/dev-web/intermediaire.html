Making the pieces talk to each other, storing data, and going live.

Introduction

The beginner level described the bricks: HTML, CSS, JavaScript, the difference between what runs in the browser and what runs on a server, and adapting to screens.

This level is about what turns a page into an application: how the pieces talk to each other, where the data lives, how all of it reaches visitors, and how to work with others without getting in each other's way. These are the four subjects on which a personal project becomes a real one.

Warning

This guide is educational and independent of fashionable technologies. The principles set out here hold whatever the language or framework; tools change, mechanisms much less.

What makes an application

🔌 APIs and JSON

An API is the point of contact between two programs. On the web it almost always takes the same shape: the browser sends a request to an address, the server returns structured data — most often in JSON format.

A contract, not just an address

A well-designed API defines four things: the address and method, what you send, what you get back, and what happens when it fails. The last point is the one people forget, and it is the one that brings applications down in production.

Status codes have precise meanings: 200 all is well, 400 the request is malformed, 401 you need to identify yourself, 404 the resource does not exist, 500 the server failed. Returning 200 with an error message in the body forces every client to guess.

Worked example — the cost of round trips

A page that chains 8 API calls, each with 120 ms of network latency and 30 ms of server processing.

In sequence: 1,200 ms. In parallel, when the calls do not depend on each other: about 150 ms.

The server is no faster in the second case. It is the arrangement of the calls that changes everything.

Common mistake — the API key in browser code

Everything the browser receives can be read: the JavaScript, the variables, the headers. A secret key placed there is public, even "minified".

Calls that need a secret must go through your own server, which holds the key and relays the request.

💡 A page's timing depends mostly on the number of round trips, rarely on the server's speed.

🗄️ Databases

As soon as an application keeps something between two visits, it needs a database. The choice of type matters less than people say; the way you query it matters enormously.

Relational or document

A relational database arranges data into tables linked to one another, with a schema defined in advance. It guarantees consistency: you cannot record an order without an existing customer.

A document database stores complete objects, with no imposed schema. It is more flexible at the start, and moves responsibility for consistency into the code.

For the great majority of projects, relational remains the reasonable default: data almost always ends up having relationships, and it is better for the database to enforce them.

Worked example — the problem of queries in a loop

Displaying 50 articles with their author's name.

One query per author: 1 query for the articles, then 50 queries. At 4 ms each, that makes 204 ms.

A single query with a join: about 6 ms.

The ratio is 34 to 1. At 500 articles it becomes catastrophic — while the code looks identical.

Indexes, and their price

An index speeds up searching on a column, like the index of a book. Without one, the database goes through every row. With one, it goes straight to the right place.

The price: every index slows writes down a little and takes up space. Index the columns used in filters and joins, not all of them.

Common mistake — building a query by gluing text together

Assembling a query by concatenating what the user typed opens the door to SQL injection — one of the oldest and most exploited vulnerabilities.

The defence is simple and systematic: prepared statements, where values are passed separately from the query text. There is no reason to do otherwise, ever.

💡 A query inside a loop is the most common performance fault, and the least visible when reading the code.

🚀 Going live

A site that works on your machine does not work yet. Going live adds constraints that local development hides entirely.

The four elements

A domain name, rented by the year. Hosting, which runs your code and serves your files. A certificate, which turns on HTTPS — today free and automatic with most hosts. A way of deploying, that is, sending a new version without breaking the previous one.

For a site with no server code, static hosting is enough: it is often free, very fast, and has almost nothing to maintain.

What changes between local and production

Paths are not the same. A link that works locally can point nowhere once online.

Casing matters. Windows does not tell Image.png from image.png; the server does. It is the most frequent failure of a first deployment.

Secrets can no longer sit in the code: they go through environment variables.

Caching appears. A change can seem absent when it has in fact been deployed.

Common mistake — deploying by copying a few files

Manually sending "the changed files" sooner or later means forgetting one. The site then references a missing script, and breaks for everyone.

Always deploy the whole thing, from a single source — ideally automatically, from the code repository.

💡 The difference between "it works on my machine" and "it is live" comes down to four points, all checkable in one go.

🧰 Working with others

Git is presented as a backup tool. That is inaccurate and it leads to using it badly. Git is for going back and for working with others on the same code without getting in each other's way.

What a good history allows

A readable history answers concrete questions: when did this line change, why, and what else moved at the same time. That requires commits that are small, coherent, and accompanied by a message explaining the why rather than the what.

"Fix VAT calculation on partial refunds" is worth infinitely more than "fix". The second forces you to read the code to understand.

Branches

A branch isolates work in progress. The principle: the main branch always stays working, and each piece of work lives alongside until it is ready.

A branch that lives three weeks becomes very hard to merge back: everything else moved meanwhile. Short branches, merged often, avoid most conflicts.

What really protects you

Never commit secrets. A password pushed once stays in the history, even if deleted afterwards. It must be considered compromised and changed.

An ignore file from day one: dependencies, local configuration files, logs.

Review before merging. Even alone: rereading your own change an hour after writing it brings out what you had stopped seeing.

Common mistake — the catch-all commit

A commit mixing a fix, a new feature and a reformatting of the code is impossible to undo cleanly: you cannot take one out without the others.

One commit, one intention. That is what makes the history usable the day something has to be undone.

💡 Git does not protect you from losing files. It protects you from being unable to go back.

📚 Going further

  • MDN Web Docs: the reference on HTTP, status codes and browser APIs. Free, ad-free, community-maintained.
  • The official Git documentation: the chapter on branching and merging, clearer than most tutorials.
  • OWASP: the list of the most widespread vulnerabilities, including SQL injection. Read it before writing a query, not after.
  • Your host's documentation: environment variables and automatic deployment from a repository. Two hours that save months.

A useful habit: as soon as a page seems slow, count the number of queries it triggers before optimising anything else.
